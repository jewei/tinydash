# Desktop IPC permissions

TinyDash's custom Tauri commands are subject to the application ACL. The [build script](../../src-tauri/build.rs) declares the complete `AppManifest` command inventory. Without an application manifest, restricting plugin permissions alone does not restrict local calls to custom commands.

The [window permission sets](../../src-tauri/permissions/windows.toml) have no default grant. The [main capability](../../src-tauri/capabilities/main.json) grants `launcher` and `shared` only to the local `main` window. The [settings capability](../../src-tauri/capabilities/settings.json) grants `settings` and `shared` only to the local `settings` window. No remote origin or wildcard window is granted access. Per-command permissions are generated by Tauri from `build.rs`; the generated files are not maintained by hand.

## Command ownership

`drag_result` and `share_result` are main-window-only commands. They accept a catalog result ID and resolve file paths or share content in Rust. Share rejects generated password IDs and text larger than 64 KiB. Native transfers block automatic launcher hiding until the session ends.

The grants follow actual frontend callers, not the module that implements a command. Calls go through [the frontend bridge](../../src/bridge.ts) and the file, library, clipboard-format, and utility bridges beside it.

The launcher cannot replace settings, preview settings imports, export settings, record shortcuts, or install updates. Settings cannot search, execute result actions, read clipboard entries, or operate the launcher. Rust tray/startup calls do not cross the frontend IPC boundary and do not require extra frontend permissions.

## Events and core commands

Both windows can listen and unlisten. Only `main` can call the native window-drag command. Neither window can call arbitrary core event emission, create windows, or directly use updater, opener, dialog, or clipboard plugin IPC. Rust commands use these plugins internally when needed.

The legitimate cross-window frontend events are `appearance-changed`, `compact-changed`, and `system-glass-changed`. Previously the frontend emitted these directly. The [typed Rust relay](../../src-tauri/src/appearance.rs) now accepts only a known theme or a boolean compact/glass value and emits the corresponding fixed event to the two application windows. It accepts neither a caller-selected event name nor a target. Main changes themes and Compact; Settings also changes Follow macOS Liquid Glass and applies saved appearance imports. Storage notifications remain a fallback. Import previews do not broadcast until Save changes.

Other events originate in Rust: `settings-changed` reaches both windows; launcher visibility/category and app/file/currency/usage/pin/clipboard changes drive the main window. These flows require subscription permissions, not frontend emit permission. In Tauri 2.11.5 the core emit implementation does not enforce event-name scopes, so adding a scope object to `allow-emit` would not provide the same protection as the typed relay.

## Changing or testing the boundary

For a new command, update the handler registration in `src-tauri/src/lib.rs`, the inventory in `src-tauri/build.rs`, the appropriate permission set, and the independent expected window matrix in `src-tauri/src/acl_tests.rs`. Do not grant an entire plugin or both windows merely to make a test pass.

```sh
bun run test:rust -- acl_tests
bun run verify:browser tests/appearance-sync.spec.ts tests/settings.spec.ts tests/launcher.spec.ts
bun run verify:browser tests/ipc-contract.spec.ts tests/ipc-drift.spec.ts
```

The Rust tests use Tauri's `get_ipc_response` and `MockRuntime` with the same generated context as production. They exercise the actual IPC authorization path, verifying every application command against both windows, unknown windows, and remote origins. Rejected calls must fail with an ACL error before a side-effect-free handler is reached. Additional tests cover unlisted commands, plugin/event rejection, real event subscription, main-only drag resolution, and the real typed relay's target/payload validation. The manifest/handler inventory assertion supplements these execution tests; it does not replace them. Tauri 3's mock runtime uses `tauri://localhost` on all platforms. The real Windows Wry runtime uses its HTTP mapping; the native suite must check that integration.

On Windows MSVC, `build.rs` embeds the Common Controls v6 dependency in every linked executable, including the library unit-test harness. Tauri's default resource helper only attaches its manifest to binary targets; the IPC tests also link native menu code that imports v6-only entry points. Missing this dependency causes a loader failure before any test can run. A Windows-only regression checks that the loaded Common Controls module exports `TaskDialogIndirect`. This OS application manifest is separate from Tauri's command ACL `AppManifest`.

The browser tests drive both views with a target-aware mocked relay and suppress storage notifications to ensure those notifications cannot hide a missing IPC call. They cover both synchronization directions, exactly one callback per change and window, the glass preference, and import preview versus save. They prove frontend behavior, not native IPC or OS effects. Actual installed-window synchronization, dragging, dialogs, and updates still require desktop/CI checks under the [verification procedure](../how-to/verify.md).

The original implementation used Tauri 2.11.5 and tauri-build 2.6.3. The [preview migration](../explanation/dependency-previews.md) keeps the same production-context ACL tests and includes every new native command in their window matrix. The test dependency uses the same Tauri version as the application. The IPC contract tests derive declarations from Rust and compare all frontend bridges, including wrapper-supplied confirmation and default arguments.
