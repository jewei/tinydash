# Data storage and privacy

TinyDash keeps settings in a JSON file and saved state in a local SQLite database. Clipboard history can contain private text. It is not encrypted. Content that its source marks as secret is not saved; see [Clipboard history](../reference/features/clipboard.md#secrets). Capture starts only after the user enables it on a fresh installation. Turning capture off keeps saved entries until they are cleared.

Currency refresh downloads a shared rate table. Search text, amounts, clipboard text, and file paths are not part of that request. Web search opens a URL only when the user chooses the action. URL cleaning and the other local tools work offline.

## Usage and ranking

The **All** mode ranks text results in two groups. First come names that equal or start with the query, including app aliases. Then come fuzzy matches, such as letters spread through a name or a path. Inside each group, results stay together by category, in this order: Apps, Files, System, Clipboard, then Emoji. So `sa` puts Safari above the exact emoji shortcode `:sa:`, and an exact filename appears above apps that match only by letters in their path. A prefix of at least two characters from a system command name or alias puts System first in each group. This includes complete names and aliases. For example, `sl`, `sle`, `re`, and `shu` keep their commands visible when app or file matches fill the 30-result limit. Valid calculations appear before these groups. Explicit tool commands and the `:` and `=` prefixes keep their own search scope. In All, an app whose name equals the query appears before the tool results, so `google chrome` finds Google Chrome before the web search. Apps whose names start with the query follow the tool results, so `time` still finds Time Machine. Ranking applies before the result limit.

Successful app launches, file opens, emoji copies, and accepted system commands update a use count and last-used time. Frequently used and recently used results move higher within their category. This also applies when the search field is empty. Exact and prefix match bonuses still favor close matches within each category. A usage bonus cannot add an item that does not match the query.

The frequency bonus is 25 points per use, up to 500 points. The recency bonus starts at 500 points and decreases with the number of days since the last use. Their combined limit is 1,000 points, compared with 10,000 for an exact match and 2,000 for a prefix match. Results with equal scores in the same category retain their existing order.

TinyDash stores `result_id`, `use_count`, and `last_used_at` in `tinydash.sqlite3`:

| Platform | Default database location                                                                                           |
| -------- | ------------------------------------------------------------------------------------------------------------------- |
| macOS    | `~/Library/Application Support/dev.tinydash.launcher/tinydash.sqlite3`                                              |
| Windows  | `%APPDATA%\dev.tinydash.launcher\tinydash.sqlite3`                                                                  |
| Linux    | `$XDG_DATA_HOME/dev.tinydash.launcher/tinydash.sqlite3`, or `~/.local/share/dev.tinydash.launcher/tinydash.sqlite3` |

Opening a location, failed actions, and calculation copies do not change usage counts. Calculation IDs are temporary. Tool pins store the input needed to run that tool again. Other search queries are not stored. Copied calculation results can enter clipboard history while capture is enabled. App and file usage is tied to the indexed path; moving an item gives it a new ID. File usage IDs contain the full path.

The database loads on a background worker; initialization can retry after temporary SQLite contention. Search uses an in-memory copy and performs no database reads while typing. SQLite writes use one connection, a short lock timeout, and explicit transactions for schema migrations, clipboard capture with pruning, and conditional sensitive cleanup. The existing macOS/Windows clipboard monitor retries pending cleanup even when clipboard contents do not change; there is no separate database polling timer. SQLite is bundled through [rusqlite](https://docs.rs/rusqlite/0.40.2/rusqlite/), so users do not need a separate SQLite installation.

If SQLite is temporarily busy or locked, TinyDash shows a warning and retries on the next storage operation. Pending ranking changes are retained and persisted after recovery; clipboard capture resumes with newly copied text. A failed user delete or clear reports an error and retains the entries until the user retries successfully; it is never queued for automatic execution. Other storage failures pause capture and keep ranking changes session-only. TinyDash leaves an unreadable or newer database intact; fix the file access or compatibility problem and restart to restore persistence. To reset all stored data, quit TinyDash, move `tinydash.sqlite3` to a backup location, then reopen the app.

Automatic sensitive cleanup after an upstream clipboard clear retains up to 64 ID/revision pairs, without text, in session memory. Matching unpinned captures are retried by the macOS/Windows monitor; pinned captures remain pending, and independently recaptured rows are protected by a revision check. Unrelated storage success cannot hide the pending privacy warning. Capture pauses at capacity; defensive overflow requires a successful full history clear. Permanent storage errors stop retries without dismissing the warning. There is no shutdown drain or durable cleanup queue: quitting or crashing loses pending intentions and warnings, and a restart can leave their text in history. Inspect and explicitly clear retained history after recovery. See [Clipboard storage contention](../reference/features/clipboard.md#storage-contention) for the limits and pin/unpin policy. SQLite secure deletion does not remove copies in recovery archives or filesystem snapshots.

## Recovery

Before migrating an existing versioned database, TinyDash creates a checked recovery archive. It does not restore it automatically. Schema 6 adds a positive integer `capture_revision` to each clipboard row, initially 1 for existing rows. Every successful capture increments the revision of deduplicated text; touches, pins, creation timestamps, and display order do not define capture identity. AUTOINCREMENT IDs prevent a deleted row's identity from being reused. Revision overflow fails the capture transaction instead of wrapping. The revision remains internal to SQLite and is not sent over IPC. Follow [data recovery](../how-to/recover-data.md) to inspect and restore an archive. Its pre-migration snapshot may retain clipboard text that is subsequently deleted.
